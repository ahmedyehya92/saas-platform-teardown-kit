# Contributing to the SaaS Platform Teardown Kit

Improvements to the methodology are welcome. This kit is a research
playbook first and a prompt package second — changes should make teardowns
more truthful, more reproducible, or easier to run, in that order.

## Repo layout

- `saas-platform-teardown/` is the skill: `SKILL.md` (orchestrator),
  `references/` (phase playbooks), `assets/report-template/` (report
  skeleton). Everything else in the repo is packaging around it.
- `examples/` holds generated teardowns. **Never hand-edit an example.**
  Examples are regenerated by running the finished kit, and only on
  minor-version milestones. Treat them as point-in-time snapshots, not
  documentation to keep current.

## Playbook prose conventions

- Terse imperative voice. The reader of a playbook is a Claude session
  mid-run — every sentence is either an instruction or a check.
- One canonical location per rule. If two playbooks need the same rule,
  one file owns it and the other points at it (see the no-credential
  access ladder: defined once in `references/02`, cited everywhere else).
- Keep sections short enough to be loaded per phase. Depth lives in the
  reference file for that phase, not in `SKILL.md`.

## Proposing a new research sweep

Sweeps live in `references/06-agy-search-playbook.md` and are engine-agnostic —
they run identically through the built-in WebSearch/WebFetch path or the
optional `agy` path. Keep every sweep in the house shape:

1. **Role** — who the subagent is pretending to be ("You are a product
   research analyst…").
2. **One exact question** — a sweep answers one question, not a topic.
3. **Required sourcing** — named sources, and "not found" over guessing.
4. **Output shape** — what comes back and how facts are separated from
   estimates.

For revenue/business-scale sweeps additionally: estimates stay separated
per source (never merged or averaged), and funding rounds are facts while
any revenue multiple attached to them is an assumption.

## Before opening a PR

1. `bash scripts/validate-skill.sh` — structural checks (frontmatter,
   sequential references, cross-reference resolution, phase-table
   invariant, template links, vocabulary). It must exit 0.
2. CI green: markdownlint (house config in `.markdownlint.json`) and a
   link check over the kit docs.
3. **Re-run a smoke teardown before proposing playbook changes** — run the
   skill end to end on a small SaaS product with your change applied.
   Methodology edits that were never executed tend to read well and run
   badly.

## If you develop against an installed copy

The skill is designed to be installed at `~/.claude/skills/saas-platform-
teardown/`. Keep the repo as the source of truth and sync with:

```bash
rsync -rv --delete saas-platform-teardown/ ~/.claude/skills/saas-platform-teardown/
```

Restart Claude Code (or start a new session) after syncing — skills load
at session start.

## Versioning convention

- **patch** — wording and clarification only.
- **minor** — new/changed sweeps, methodology changes, new examples.
- **major** — output-contract or phase-structure changes.

See `CHANGELOG.md` for the history.
